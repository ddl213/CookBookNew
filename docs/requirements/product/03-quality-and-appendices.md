## 4. 页面样式和交互

### 4.1 视觉风格

【原有需求】

- **整体色调**：简洁、清爽的白色背景，搭配明亮、温暖的橘色、黄色。
- **内容呈现**：主要内容采用圆角、适度阴影的卡片式设计。
- **图标**：导航和主要功能按钮使用简洁图标并搭配必要的文字说明。
- **字体**：全局风格统一，用字号、粗细区分内容层级。
- **图片**：菜品图片清晰、完整且具有吸引力。
- **操作反馈**：按钮点击提供明显的按压或状态变化反馈。

【落实说明】优先复用同一 App 中已有的卡片、按钮、导航、空状态与弹窗样式，避免页面之间出现无依据的视觉分裂。具体尺寸、字号、间距、色值和插图以设计稿及项目现有规范为准，不在需求文档中臆造固定像素值。

### 4.2 关键交互一致性

1. **首页折叠行为**：展开搜索框与折叠后搜索按钮指向同一搜索能力；分类标签在滚动切换时保持可识别、可点击。
2. **菜谱内容**：卡片点击进入详情；头像点击进入相应用户主页；同一数据在不同入口看到的核心信息应一致。
3. **预订入口**：保留“加入购物车”按钮与“预订确认弹窗”的原始交互，不自动引入独立购物车或结算页。
4. **订单操作**：提交时应给出处理反馈；因网络故障或后台拒绝而失败时，不应显示为成功。
5. **权限变化**：当菜谱可见性、好友关系或登录状态改变时，相关内容应重新按权限判断。
6. **列表和详情**：提供基本加载、无内容和请求失败反馈；不增加原文未定义的独立业务状态。

### 4.3 适配与易用性

【落实说明】界面应兼容不同 Android 屏幕尺寸、文字长度和系统字体缩放；长菜名、长昵称、较多食材步骤不应遮挡主要操作。网络较慢时优先保证页面可反馈、操作不重复提交。具体布局实现遵守项目现有的 Android 开发规范，不在本 PRD 中强行指定新的架构或组件方案。

## 5. 非功能性需求

### 5.1 性能

**并发处理【原有需求】**：热门菜谱、公共列表与好友动态等高访问内容，应支持并发加载，保障日常浏览流畅。

**加载速度【原有需求】**：页面在正常和弱网条件下应具有合理响应；对菜谱图片、列表数据及重复请求进行必要优化。

【落实说明】同一操作不应产生非预期的重复菜谱或重复订单；图片加载失败不应导致整个页面无法浏览。原文未规定首页首屏耗时、接口 SLA 或支持并发人数等数值指标，需要在技术评估后另行确认。

### 5.2 安全与隐私

**用户数据【原有需求】**：个人资料、聊天记录等敏感数据应加密存储和传输。

**登录鉴权【原有需求】**：登录、注册及身份验证需要安全可靠，防止非授权访问。

**访问控制【落实说明】**：菜谱可见范围、聊天双方、订单相关方和用户资料隐私应在数据访问环节校验，不仅依赖前端按钮显示。

**支付安全【未来规划】**：未来引入收费预订时，必须遵守相应支付规范和安全要求；当前免费预订不依赖支付功能。

### 5.3 可扩展性

**模块化【原有需求】**：架构应便于未来增加群聊、菜谱直播、美食社区等功能。

**配置管理【原有需求】**：预订限制等可扩展能力应支持后台配置的可能性，方便后续运营调整。

【落实说明】本期仅保持可扩展空间，不因此提前实现群聊、直播、社区、收费结算等未来模块。

### 5.4 数据一致性与异常恢复

【落实说明】

- 用户更新菜谱或个人资料后，刷新相关入口应能获取一致的当前数据。
- 预订创建、接受或拒绝完成后，双方订单视角展示的数据应保持一致。
- 网络超时或页面被关闭时，不能仅依据客户端是否收到响应就假定订单创建成功或失败；重试与状态回查方式由接口设计确定。
- 页面加载失败可重试，且重试不能绕过权限校验或造成重复业务操作。

## 附录 A. 核心流程梳理（不改变现有业务）

### A1. 菜谱发布与浏览

`创建菜谱 → 设置可见性 → 发布后出现在个人菜谱列表 → 有权限的用户从首页/公共内容/分享等入口查看 → 进入菜谱详情 → 收藏、评论或分享`

- 已确定：菜谱由创建者维护，可见性为好友可见或所有人可见。
- 落实重点：不同入口统一权限，菜谱修改后同步更新展示。
- 未确定：编辑页字段校验、草稿、图片数量、发布审核等。

### A2. 好友聊天与分享

`好友关系 → 消息页 → 进入聊天详情 → 一对一聊天`  
`菜谱详情 → 分享弹窗 → 将菜谱分享给好友 → 好友按可见权限访问`

- 已确定：一对一好友聊天、菜谱分享给好友。
- 未确定：好友申请流程、分享载体形式、消息回执规则等。

### A3. 菜品预订

`好友可预订菜品 / 菜谱详情 → 加入购物车（预订入口） → 预订确认弹窗 → 提交预订 → 我的订单 / 我的销售 → 创作者接受或拒绝 → 后续订单处理`

- 已确定：现阶段免费、仅好友间预订、创作者可接受或拒绝、可管理备货。
- 已确定：订单列表存在“待接受”“待取货”等状态。
- 未确定：完整状态图、数量、取消、交付及完结条件。不得根据示意流程自行补齐为既定规则。

### A4. 内容发现

`首页推荐 / 好友动态 / 热门 / 分类标签 → 菜谱详情`  
`推荐大师 / 公开菜谱 → 创作者主页或菜谱详情`

- 已确定：按用户偏好和浏览历史推荐内容；支持好友动态、公开菜谱和分类浏览。
- 未确定：算法权重、冷启动、热门定义、附近排序等。

## 附录 B. 订单与预订规则边界

### B1. 已确认的业务事实

| 事项 | 当前需求 |
| --- | --- |
| 谁可以预订 | 好友之间可互相预订符合条件的菜品 |
| 是否收费 | 当前免费；付费属于未来规划 |
| 预订入口 | 菜谱详情 / 菜品预订详情的“加入购物车”按钮 |
| 预订确认 | 点击入口进入预订确认弹窗 |
| 预订方管理 | “我的订单” |
| 提供方管理 | “我的销售”，可接受、拒绝并处理备货 |
| 已举例的状态 | “待接受”“待取货” |
| 后续扩展 | 语音、视频、文字等条件或收费，尚未确定当前实现 |

### B2. 状态与操作的待确认项目

**目前无法根据原文确定完整订单状态机。** 为防止不同端自行假设，请在接口与页面联调前确认以下事项：

| 待确认事项 | 需要明确的决策 | 未确认前的处理原则 |
| --- | --- | --- |
| 创建订单 | 确认弹窗提交后何时生成订单 | 只按成功响应或可靠回查展示创建结果 |
| 接单 / 拒单 | 哪些状态允许接受或拒绝 | 由有效订单状态控制操作，不预置自定义状态名 |
| 备货与取货 | “待取货”如何进入、由谁推进 | 不自行加入配送/确认收货流程 |
| 取消订单 | 用户能否取消，取消条件是什么 | 不默认开发取消按钮 |
| 订单完成 | 何时算完成、谁来确认 | 不自动定义完成标准 |
| 订单变更 | 菜谱后续编辑/删除影响已有订单吗 | 历史订单展示策略需单独确认 |
| 预订内容 | 数量、备注、多菜品和特殊条件 | 按设计稿已有字段实现，未给出不得扩展 |
| 通知 | 何时触发、通过什么消息形式传达 | 保留消息页可展示预订通知的原有能力 |
| 时间与评分 | 预计送达时间、好友评分来源 | 不展示虚构的业务结果 |

### B3. 一致性原则

无论订单从“我的订单”“我的销售”还是消息通知进入，查看的应是同一笔关联订单。服务端负责最终状态与权限判定；客户端显示处理进度与结果，不在界面本地凭空改变订单最终状态。

## 附录 C. 核心功能验收清单

> 以下清单仅检验文档中已经明确的功能及必要的一致性，不把附录 B 的待确认事项当作已定功能。

### C1. 用户与菜谱

- [ ] 同一用户可以浏览别人的菜谱，也可以发布和管理自己的菜谱，无须切换独立账号角色。
- [ ] 个人菜谱页只展示当前用户发布的菜谱；创建、编辑和删除结果能正确更新。
- [ ] 好友可见菜谱不能通过公开列表、搜索或分享链接被无权限用户读取。
- [ ] 所有人可见菜谱可在对应公共内容入口展示。
- [ ] 菜谱详情包含图片、名称、作者、简介、食材清单和制作步骤。
- [ ] 评论、收藏、分享使用当前有效的菜谱和权限信息；收藏与个人收藏列表一致。

### C2. 首页与内容发现

- [ ] 首页有搜索框、分类标签、菜谱卡片及好友动态入口。
- [ ] 上滑时搜索框按原型折叠，折叠后分类标签右侧出现可用的搜索按钮。
- [ ] “推荐”“好友动态”“热门”“家常菜”“早餐”“甜品”等分类可以按原有设计切换内容。
- [ ] 菜谱卡片可进入详情，好友动态头像可进入好友主页。
- [ ] “推荐大师 / 公开菜谱”可以切换对应内容，创作者卡片与公开菜谱支持详情跳转。

### C3. 社交与预订

- [ ] 好友之间可以进入一对一聊天；消息页展示相关聊天记录和预订通知。
- [ ] 预订入口保留原文案与确认弹窗，不强制要求独立购物车或支付结算页。
- [ ] 当前菜品预订只面向符合条件的好友，不因菜谱公开而自动开放陌生人下单。
- [ ] 成功提交的预订可以在预订方“我的订单”和提供方“我的销售”中对应查看。
- [ ] 提供方能够接受或拒绝符合操作条件的预订，操作结果与双方列表一致。
- [ ] 列表与订单详情可展示原设计中明确的订单状态，例如“待接受”“待取货”。

### C4. 我的与通用交互

- [ ] “我的”页展示头像、昵称、ID，以及收藏、好友、订单和设置入口。
- [ ] 未登录时按原设计展示“登录/注册”和“浏览应用”。
- [ ] 各页面可处理必要的加载中、无内容和网络失败情况，用户不会误以为操作已经成功。
- [ ] 不同屏幕和较长文本情况下，核心内容与主要操作不存在遮挡、溢出或重叠。
- [ ] 现阶段的免费预订不依赖付费或未来的交换条件功能。

## 附录 D. 待确认事项与优先级

以下不是新增功能清单，而是**原有需求尚未定义清楚、实现前可能产生分歧的细节**。

| 优先级 | 问题 | 影响范围 |

3. 中低优先级未决事项可在相应页面实现前确认，不阻碍已明确功能的推进。
