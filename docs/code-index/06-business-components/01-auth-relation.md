# 06-01 · 登录态、会话与关系操作

> 返回分类首页：[06-business-components.md](../06-business-components.md)。菜谱与首页/创作者展示见 [02-recipes-index.md](02-recipes-index.md)。

**收录范围：**跨页面复用的登录态、认证表单校验、用户主页操作决策、好友申请状态与关系页 UI 工具。

| ID | 类 / API / 资源入口 | 用途与优先复用场景 | 调用方式、前提和限制 | 定义文件（项目相对路径） | 真实调用位置 / 核查证据 |
| --- | --- | --- | --- | --- | --- |
| BIZ-001 | `SessionManager.state`、`restore/login/register/logout/currentToken` | 全局登录态入口：启动恢复、登录、注册、退出；页面通过同一个 `StateFlow<AuthState>` 渲染，避免各自维护登录状态。 | Kotlin `object` 进程内单例；`state` 初始 `Unknown`，UI 不能把 Unknown 当作未登录。`restore()` 有缓存时先发 `LoggedIn(cached)` 再请求 `/auth/me`；401 清会话，网络失败但有缓存时保持登录，无缓存则 `LoggedOut`。`login/register` 为 suspend，成功后保存 token/用户并更新状态；`logout()` 同步清本地会话并递增 generation，防止进行中的 restore 写回。内部 `Mutex` 串行化会话操作；调用方需在协程中执行，UI 收集应使用 `repeatOnLifecycle(STARTED)`。 | `subModules/lib_network/src/main/java/com/example/network/session/SessionManager.kt` | `MainActivity.initData` 调用 `restore()`；`LoginFragment`/`RegisterFragment` 调用 `login/register`；`MineFragment` 收集 `state` 并调用 `logout()`；`FriendsFragment`、`FriendSearchFragment`、`FriendRequestsFragment`、`UserProfileFragment`、`CookBookChildFragment` 收集 `state`，401 时统一 `logout()`；`AddRecipesFragment` 在请求 401 时登出并返回；底部鉴权头见 DATA-004，Repository 见 DATA-010。 |
| BIZ-002 | `AuthState`（`Unknown` / `LoggedOut` / `LoggedIn`） | 页面统一消费的登录态模型，配合 BIZ-001 做加载、未登录、已登录三态切换。 | `sealed interface`；`LoggedIn` 持有 DATA-007 `UserDto`。`Unknown` 只表示启动恢复尚未完成，应显示过渡状态而不是“未登录”；`LoggedOut` 才是确定未登录。页面应在 view 存在时再更新控件。 | `subModules/lib_network/src/main/java/com/example/network/session/AuthState.kt` | `SessionManager` 发射三种状态；`MineFragment.render()` 对三种状态做穷尽 `when` 并切换 `pbSession`、`llLoggedOut`、`llLoggedIn`。 |
| BIZ-003 | `AuthValidator.validateLogin/validateRegister`、`ValidationResult` | 登录/注册表单的纯 Kotlin 预校验，在发请求前给出字段提示；不替代后端校验。 | 用户名校验前 trim，长度 3-32；密码不 trim、至少 6 位；昵称 trim 后可选、最多 32；注册确认密码必填且必须一致。返回 `ValidationResult(isValid, errorMessage?)`，用 `valid`/`invalid(message)` 构造。规则与后端可能变化，服务端 400 仍由 DATA-009 映射。 | `subModules/lib_auth/src/main/java/com/rhys/auth/AuthValidator.kt` | `LoginFragment.submitLogin()`、`RegisterFragment.submitRegister()` 调用；`AuthValidatorTest` 12 例（TEST-005）。 |
| BIZ-004 | `UserProfileActionResolver.resolve`、`UserProfileAction` | 根据登录态、是否本人、是否好友决定用户主页关系操作区；新用户主页/他人资料页可直接复用。 | 纯 Kotlin `object`，只做 UI 决策，不访问网络、不替代后端权限校验。优先级：未登录 → `LOGIN_REQUIRED`；本人 → `NONE`；好友 → `MESSAGE_AND_UNFRIEND`；非好友 → `ADD_FRIEND`。未登录时页面不得展示私有数据；操作结果仍以接口返回和后端判定为准。 | `subModules/lib_relation/src/main/java/com/rhys/relation/model/UserProfileActionResolver.kt` | `UserProfileFragment.renderProfile()` 根据结果切换加好友/发消息/解除好友按钮；`UserProfileActionResolverTest` 4 例（TEST-007）。 |
| BIZ-005 | `FriendRequestStatus.fromRaw`、`isPending` | 把后端 `pending/accepted/rejected` 转为可操作状态，避免把未知状态误判为可处理。 | `enum class` 含 `UNKNOWN`；`fromRaw` 忽略大小写，未知/null/空白归为 `UNKNOWN`；只有 `PENDING` 的 `isPending` 为 true。页面仅在“收到且 pending”时显示接受/拒绝；状态文案由页面映射，不能凭 raw 字符串自行扩展业务状态。 | `subModules/lib_relation/src/main/java/com/rhys/relation/model/FriendRequestStatus.kt` | `FriendRequestsFragment.bind` 决定按钮显隐与可操作性，`statusText()` 映射文案；`FriendRequestStatusTest` 3 例（TEST-008）。 |
| BIZ-006 | `RelationUiSupport`（`bindRelationAvatar`、`firstCharacter`、`openUserProfile`、`openLoginPage`、`readUserIdArgument`） | `lib_relation` 内复用头像占位、昵称首字、用户主页/登录页跳转与 `userId` 参数读取，减少四个页面的重复逻辑。 | 全部为 `internal`，只在 `lib_relation` 模块内可见，不能跨模块复用；头像加载见 UTIL-005、URL 解析见 DATA-003；`openUserProfile` 需要有效 `NavController`，`userId <= 0` 时 no-op；`readUserIdArgument` 兼容 Bundle 与 deep link query，非法值返回 0，页面需显示用户不存在。参数契约见 ARCH-012。 | `subModules/lib_relation/src/main/java/com/rhys/relation/RelationUiSupport.kt` | `FriendsFragment`、`FriendSearchFragment`、`FriendRequestsFragment`、`UserProfileFragment` 调用；`readUserIdArgument` 供 `UserProfileFragment.userId` 使用。 |
