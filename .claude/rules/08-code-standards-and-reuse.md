# Android 代码规范：先盘点、优先复用、分类索引、增量维护

> 适用范围：美食家园 Android 项目及相关本地模块。与 `CLAUDE.md`、其他 `.claude/rules/` 同时生效。代码索引不是产品阶段索引，不得把能力明细写进 `docs/PROGRESS.md` 或 `docs/CURRENT_TASK.md`。

## 1. 强制执行顺序

1. Root 每次开发前**先读** `docs/code-index/00-INDEX.md`，按本次功能阅读对应分类表；并读取当前阶段的需求/进度。未完成首次盘点时，先派 `code-auditor` 完成盘点，才允许依赖“可复用能力已知”这一前提开展新功能实施。仅限与盘点无关且已经批准的工作可独立推进。
2. 查索引命中的同类工具、扩展方法、自定义 View、通用布局、Adapter、Repository、现有依赖及实现模式；以**实际源码**核对 API、使用前提和当前适用性，然后复用。索引是查找入口，不是可以直接复制而不检查的真理。
3. 优先级：**项目已验证的同功能实现 → 项目已引入的库/通用组件 → 在既有架构内做最小扩展 → 必要时新增实现**。新建类、封装、View、依赖前须确认索引没有合适能力；不为“代码更漂亮”重写已稳定功能。
4. 当前任务结束前，交 `code-auditor` 用**本任务实际改动文件清单**更新分类表；由 Root 核对代码/索引一致，再交独立验证与进度归档。删除、移动、重命名、签名/行为变化必须修正旧条目，不留指向不存在文件的记录。
5. **禁止每个任务重新全仓扫描**。首次核实基线后，只按分类索引定位、验证具体实现，以及检查任务差异；只有发生重大目录重构、明显索引污染或已确认的覆盖缺口时才由 Root 授权相关范围重新盘点，并记录原因。

## 2. 首次项目盘点：一次建立可靠基线

由 Root 将“只读源码盘点 + 生成文档索引”作为当前 P00 阶段内的独立可核查工作，交给 `code-auditor`。没有真实项目源码时不能宣称已盘点，索引保持 `未盘点`。

- **先确认实际边界**：真实仓库根目录、Gradle settings/build 文件、所有 Android/Java/Kotlin 模块与 sourceSet、现有技术栈、Git 当前变更及可能缺失的子模块。记录只读事实；不通过盘点添加依赖、改代码或清理工作树。
- **全仓文件级发现一次**：包括 Kotlin/Java、XML、Gradle 构建和版本目录、项目内脚本与构建工具。排除 `.git/`、`.gradle/`、`build/`、`.idea/`、派生产物、外部 SDK、二进制缓存及任何密钥/私人数据；留意未跟踪源码，避免只看 Git tracked 文件。
- **候选能力检索**：定位共享工具类、静态/顶层/扩展函数、Base 类、接口封装、数据转换、图片/权限/时间/网络/数据库/导航/线程工具；定位所有自定义 View、复合控件、Adapter/Delegate、布局复用、主题样式和 attrs；定位公共业务组件与测试脚手架。
- **逐项核实**：读取候选源码的真实入口、入参/返回值、生命周期与限制，必要时查看调用位置/引用关系，辨别“正在使用”“只定义未证实使用”“废弃/不推荐”。不能只从类名、注释或文件路径猜用途，不编造代码或方法签名。
- **依赖和约定**：核对当前已引入的 AndroidX/第三方库及版本来源、DI/数据库/网络/异步/UI 处理方式、项目内部对同类场景的首选实践。禁止仅为建索引下载依赖、运行宽泛测试或联网搜索代码。
- **分类登记**：只记录实际可复用、跨页面通用或有明确复用场景的能力，不逐一抄录无复用价值的私有函数、每个 drawable 和纯页面文案；保持可发现性、真实性、路径准确性。
- **完成条件**：各已存在模块均纳入盘点范围，分类表有真实路径和实际可调用性说明；列清未覆盖/无法访问范围，Root 审核后才将 `00-INDEX.md` 状态标为 `已盘点`。有缺口则标 `部分完成`，不得伪报全覆盖。盘点不等于全仓运行测试通过。

## 3. 分类索引契约

唯一能力导航入口是 `docs/code-index/00-INDEX.md`；每一类对应独立 Markdown 表格，具体类别见其导航。区分于 `docs/PROGRESS.md`（只列产品阶段名称）。

| 列 | 必须填写的内容 |
| --- | --- |
| ID | 稳定类别编号，如 `UTIL-001`、`VIEW-001`；删除/替换不复用旧编号 |
| 类/入口 | 真实类名、方法签名或资源名，能直接在工程中定位 |
| 用途及复用条件 | 适合处理什么、优先用于哪类场景；不要写空泛介绍 |
| 调用约束 | 入参/返回值、线程、生命周期、权限、适配限制、弃用信息中的相关项 |
| 源码路径 | **真实**项目根目录相对路径，使用反引号包裹，一个主定义文件 |
| 证据 | 现有调用位置、使用范例文件或源码核查依据；未证实须标明 |

- 一条描述一个**可复用能力**，必要时把同一个工具类紧密相关的方法合并为一条；不同含义和适用场景不得因类名相同而混为一条。
- 必须按功能分类，而不依赖开发者、阶段、编辑日期分类。多模块同名类用真实路径区分；跨分类不重复复制描述，保留规范主条目并从其他分类引用 ID。
- 新增可复用能力时登记；调整入口/行为/调用条件时更新原条目；删除时移除失效入口并将废弃/迁移原因记在当前阶段进度或相关变更记录，**不得让历史结论消失**。
- `00-INDEX.md` 保留分类名称、文件链接、盘点状态、覆盖与缺口，不放详细类/方法表；即使某类没有命中，也要明确标注 `无已发现项`，不是随意省略。
- 接近 **12 KiB** 时按场景拆该分类：如 `03-custom-ui/01-views.md`、`03-custom-ui/02-adapters.md`；原分类文件改成目录导航，`00-INDEX.md` 继续只索引一级类别。**单个 Markdown ≤ 16 KiB（16,384 UTF-8 bytes）**；不能摘要丢失重要约束、无提示截断或创建无限长总表。

## 4. 增量查找与同步规则

- 常规任务：Root 仅读主索引 + 相关分类；实施 Agent 按表列出的**精确路径**查实现及必要调用示例，避免从仓库根反复 `rg`/遍历。仅当索引没有候选或当前内容已经变更时，先查相关模块/目录，不做无根据全仓检索。
- 实现 Agent 在交付报告中列明：本任务复用的已有能力（ID + 路径）、确需新建的公共能力与理由、变更/删除的索引条目、实际新增/修改源码路径；不自己修改阶段索引。
- 先结束拥有相关代码文件的实施 Agent，再安排 `code-auditor` 对其变更文件及关联调用**局部复核**并维护分类表；同一索引文件不允许并行写入。`code-auditor` 不借整理索引修改业务代码。
- 索引应随对应代码任务一起进入审核和受控本地提交。检查 `python scripts/code_index_check.py check`，再运行已有的 `python scripts/phase_flow.py check`；前者只核对文档结构、条目重复/源文件路径及大小，**不能证明代码调用语义与覆盖完整**。
- 若索引缺失、疑似过期：先标记受影响类别待核对，检查目标源码/调用点、修正类别索引后继续。只有明显全局不可信或目录整体迁移才按 Root 批准范围重新盘点。

## 5. Android 代码质量规则

- **服从工程现状**：先确认现有模块边界、包结构、命名风格、Kotlin/Java 比例、架构分层、ViewBinding/DataBinding/Compose 使用情况以及 Gradle 约定。不因“推荐做法”擅自更换 MVVM/MVI、数据库、网络库、DI 框架或 Java/Kotlin 语言。
- **最小改动与复用**：优先调用现有公开工具/组件，避免同功能 `Utils2`、复制大段页面逻辑或额外第三方库。若已有实现无法满足，说明具体缺口，仅补最小必要扩展，并保持现有公共接口兼容；有破坏性变更先交 Root。
- **可维护性**：单一职责、清晰命名、减少重复逻辑及无效嵌套；只抽取真正共享且稳定的行为，不为单次调用增加过度抽象。遵循项目既有代码格式、空值处理、错误处理、日志和测试习惯。
- **Android 正确性**：按项目既有生命周期管理协程/订阅和 Context/Listener，避免阻塞主线程、泄漏 Activity/View、非预期重复注册；数据读写和 UI 状态在既有线程/作用域约定下处理。
- **业务安全**：不得在 UI 隐藏替代好友可见性或权限校验，不写入密钥或私人聊天数据至日志/仓库；订单/身份相关接口不能凭经验补造状态、支付或权限规则。
- **资源与依赖**：先复用项目已有颜色、drawable、selector、style、主题和 strings/dimens；新增依赖前核对已有库是否满足需求，且需要 Root 授权，不为单个便利方法引入新的库。对新增/改动 UI 只处理本次任务涉及范围。

## 6. Android XML 布局硬性规范

以下英文要求按用户给出的约束落实，和 `.claude/rules/06-android-layout.md` 同时适用：

> When writing Android XML layouts, give priority to using ConstraintLayout and prohibit the use of FrameLayout; only use LinearLayout when the layout is simple or a more concise implementation can be achieved, and avoid unnecessary nesting. Do not directly hard code the width and height of controls, and prioritize using wrap_content, 0dp with complete constraints, percentage or dimensionRatio to implement Self-Adaptation. Do not copy the absolute dimensions of the design draft mechanically, and ensure that there is no overflow, overlap or truncation under different screen sizes and text lengths.

- 对**新增和实际修改的 XML**，优先 `ConstraintLayout`；**不得新增 `FrameLayout`**，仅在布局简单或确实更清晰时用 `LinearLayout`，拒绝无意义层级。既有未修改的布局不为套规范强制重构。
- 非必要不直接硬编码控件宽高，优先 `wrap_content`、完整约束的 `0dp`、百分比/`dimensionRatio`；区分必须固定的规范尺寸（例如图标/点击区域）与机械抄设计稿的绝对宽高；尺寸尽可能复用项目资源。
- 充分考虑屏幕尺寸、系统字体放大、内容变长、横竖屏（若当前项目支持）、状态栏及软键盘；避免溢出、遮挡、重叠、截断关键操作。图片作为整体资源还是动态控件，以真实原型与功能需求为准。
- 项目原有布局、复制的成熟功能页应按其现有结构维护；如本次任务需要修改其中一部分，只约束实际新增/改动代码，不顺手重写不相关布局。

## 7. 交付检查与停止条件

- 首次：提交分类索引、真实模块覆盖说明、未覆盖清单、代表性入口/调用证据；不能凭只有文件名列表就写 `已盘点`。
- 日常：提交复用清单、确需新增的理由、影响路径、索引增量、最小有效代码验证及需要用户手测的 UI 步骤；索引目录属于任务交付的一部分。
- 文档规范不能绕过 Root 不直接修改代码的约束，也不能改变阶段 Gate、用户未决需求或 Git 提交门禁；如果源码缺失或风险无法消除，准确报告 `Blocked` / `Needs decision`。
