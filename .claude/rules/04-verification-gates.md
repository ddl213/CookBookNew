# 最小验证、失败与 Gate

## Root 决定验证范围

- Root 按当前任务获批范围明确完整检查清单和验收标准。“完整”指该范围的全部步骤，不默认全仓回归；每轮从头执行完整清单，不能只查修复点，也不得为获得 PASS 擅自删项、少跑或降低标准。范围或标准确需调整时，由 Root 记录原因并重新明确清单。
- 文档/非行为配置：核对引用路径、Markdown/语法、受影响文件及 `phase_flow.py check`；无须跑产品全套测试。
- 机械代码：受影响模块构建 + 至多一个必要的定向检查。
- 行为逻辑：受影响模块构建 + 必要定向验证 + 一个实际主路径烟测；Bug 尽量先最小复现再验证修复。
- 后端状态、鉴权、订单一致性：增补最小必要的拒绝路径、失败/重试/重复请求验证；不因难度大自动扩大为全仓扫描。
- 只有用户明确要求，或所有已规划功能阶段完成后进入最终集成验收，才执行全量回归、性能/压力测试、广泛自动化 UI 测试或付费在线 API 反复调用。

## 正式验证轮次（唯一详细流程）

1. 实施结果稳定后，Root 派发第一轮独立 `verifier`。每轮都由 Root 顺序派发新的测试 Agent，须不同于实现 Agent 及此前各轮测试 Agent；禁止轮次并行。轮次与同轮修复复测次数分别编号、分别记录，复测不能算新轮。
2. 当轮 verifier 先按下节完成数据重置、新数据准备及必要安装，再从头执行获批范围的完整清单，逐项记录实际结果；不得拿历史证据抵扣本轮步骤。
3. 第一轮必须完成完整清单；结果须为直接 PASS，或已发现问题全部经实施 Agent 修复、由 verifier 同轮复测通过，Root 才能派发第二轮。修复与复测由 Root 安排，verifier 不自行修复。
4. 第二轮及以后，只有某轮从头执行完整流程、全程未发现任何问题，才可作为最终干净轮次。任一轮发现问题，即使修复并同轮复测通过也不能最终放行；该轮问题全部修复复测通过后，Root 必须再派新的独立 verifier，以清空后的新数据完整重测，后续依此循环。
5. 放行至少需要两轮：首轮通过或问题修复复测关闭，所有前序问题已关闭，且第二轮或更后某轮满足上述干净条件。**不要求连续两个零问题轮次**；首轮修复复测通过、第二轮完整无问题即可满足轮次门禁。由 Root 审核证据后决定技术接受。
6. 漏项、未运行、超时、缺证据、数据清理或安装失败均不算通过；必须报告并解决，不能将该轮记为干净。仅做局部修复复测不能替代下一轮完整流程。

## 每轮与每次复测前的数据及安装

- 当轮 verifier 在正式测试及每次修复后的复测前，重置本次验证涉及的专用测试环境数据：按适用范围清空应用本地数据、测试账号/业务记录、缓存、mock 或后端测试库等，核实已清空后再准备本轮/本次复测的新数据，并记录动作、结果和证据。
- 不能沿用前轮或复测前的残留数据、导入旧快照作为起点。仅操作可确认属于测试且已获授权的范围；严禁清理生产或真实用户数据。无法清理或无法隔离时报告 `Blocked`，不得假定环境干净。
- 需要安装应用时，由**当轮 verifier 亲自执行**安装、重装或更新，并核对记录测试制品/版本、目标设备、执行人、动作与结果。实施 Agent 可以构建交付安装包，不能由 Root 或实施 Agent 代装后直接计为验证；复测涉及新制品时同样由 verifier 安装。
- 纯文档核查确实没有运行数据或安装需求时，分别记录数据重置/新数据及安装“不适用”与理由；仍须至少两个顺序、独立的文档验证轮次，不能豁免轮次门禁。

## 证据纪律

- 历史证据只可用于问题排查和同轮接续；代码/环境变化使其失效时应重新核查。已有证据不能替代必需的新轮、数据清空、新数据或本轮完整重测。
- 严格区分真实 `PASS`、预期复现 `RED`、`FAIL`、未运行/超时/缺日志。不能用工具退出标签代替错误原因分析。
- 记录轮次、Agent、复测次数、完整清单结果、数据与安装证据、问题/修复/复测及最终干净轮次；命令、真实返回、关键错误摘录、受影响范围和证据相对路径应可追溯，不复制整段日志。
- 不以重复 SHA-256 作为例行验证；仅在明确需要内容完整性、校验和或经授权的安全/缓存协议时使用。
- 同轮修复复测可聚焦 Root 确认的受影响检查，但仍须先重置数据、准备新数据，且不能抵扣后续必需的新轮完整重测。范围外异常只报告事实与影响，由 Root 决定后续，不擅自扩围。

## 阶段完成与 UI 人工验收

- `Implemented`：实现已交付，验收未完整；`Verified`：全部必需轮次满足本规则、最终干净轮次证据充分且 Root 技术接受；`Phase accepted`：用户明确接受整个阶段；`Blocked`：需要决策、外部条件或权限。
- 阶段 Gate 需要当前阶段交付、必要依赖、证据、阻塞与风险明确，不自动把下一阶段标为开始。
- 涉及 UI、布局、导航、输入、状态反馈的修改，必须随 Gate 报告：测试前提、逐步点击/输入流程、每步预期与异常路径、需要用户观察之处。等待用户手工确认。
- 已实现的功能不能因为没跑全量测试就伪称“全项目可交付”；尚未实现的后续页面也不因有占位控件而算完成。
