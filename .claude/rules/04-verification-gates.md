# 最小验证、失败与 Gate

## Root 决定验证范围

- 文档/非行为配置：核对引用路径、Markdown/语法、受影响文件及 `phase_flow.py check`；无须跑产品全套测试。
- 机械代码：受影响模块构建 + 至多一个必要的定向检查。
- 行为逻辑：受影响模块构建 + 必要定向验证 + 一个实际主路径烟测；Bug 尽量先最小复现再验证修复。
- 后端状态、鉴权、订单一致性：增补最小必要的拒绝路径、失败/重试/重复请求验证；不因难度大自动扩大为全仓扫描。
- 只有用户明确要求，或所有已规划功能阶段完成后进入最终集成验收，才执行全量回归、性能/压力测试、广泛自动化 UI 测试或付费在线 API 反复调用。

## 证据纪律

- 验证 Agent 与实现 Agent 独立；检查目标由 Root 明确授权。有效已有证据可复用，除非代码/环境变化使其失效，不为会话切换重跑。
- 严格区分真实 `PASS`、预期复现 `RED`、`FAIL`、未运行/超时/缺日志。不能用工具退出标签代替错误原因分析。
- 记录命令、真实返回、关键错误摘录、受影响范围、证据相对路径；不要复制整段日志或重复列每个 PASS。
- 不以重复 SHA-256 作为例行验证；仅在明确需要内容完整性、校验和或经授权的安全/缓存协议时使用。
- 修复后只重复受修改影响而失效的检查；出现意外结果停止扩大范围，交 Root 决定。

## 阶段完成与 UI 人工验收

- `Implemented`：实现已交付，验收未完整；`Verified`：Root 基于定向证据技术接受；`Phase accepted`：用户明确接受整个阶段；`Blocked`：需要决策、外部条件或权限。
- 阶段 Gate 需要当前阶段交付、必要依赖、证据、阻塞与风险明确，不自动把下一阶段标为开始。
- 涉及 UI、布局、导航、输入、状态反馈的修改，必须随 Gate 报告：测试前提、逐步点击/输入流程、每步预期与异常路径、需要用户观察之处。等待用户手工确认。
- 已实现的功能不能因为没跑全量测试就伪称“全项目可交付”；尚未实现的后续页面也不因有占位控件而算完成。
